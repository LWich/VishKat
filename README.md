# «ВышКат» — учёт парка кикшеринга

Учебный проект по КПО: REST API на FastAPI и консольная демонстрация той же доменной модели. Проект учитывает транспорт и вещи, проводит обязательный техосмотр транспорта, считает суточное энергопотребление и показывает устройства, безопасные для новичков.

## Быстрый запуск

Требуется Python 3.13+ и [uv](https://docs.astral.sh/uv/).

```bash
cp .env.example .env
uv sync --dev
uv run uvicorn app.main:app --reload
```

После запуска доступны:

- Swagger UI: <http://127.0.0.1:8000/docs>;
- OpenAPI: <http://127.0.0.1:8000/openapi.json>;
- проверка состояния: <http://127.0.0.1:8000/api/v1/health>.

Конфигурация читается классом `app/core/config.py::Settings` из переменных окружения и `.env` через `pydantic-settings`. Все переменные имеют префикс `VYSHKAT_`; полный пример находится в `.env.example`.

### Консольная демонстрация всех сценариев

```bash
uv run python -m app.cli
```

Сценарий показывает: успешную приёмку трёх видов транспорта, отказ техосмотра, постановку вещей на баланс, количество объектов, суммарную энергию, список транспорта для новичков и полную инвентарную ведомость.

## Примеры API

Добавить самокат (техосмотр выполняется до сохранения):

```bash
curl -X POST http://127.0.0.1:8000/api/v1/vehicles \
  -H 'Content-Type: application/json' \
  -d '{
    "type": "scooter",
    "inventory_number": "SC-001",
    "name": "Самокат у корпуса A",
    "beginner_ease": 8,
    "daily_energy_kwh": 1.8
  }'
```

Добавить шлем:

```bash
curl -X POST http://127.0.0.1:8000/api/v1/items \
  -H 'Content-Type: application/json' \
  -d '{"type":"helmet","inventory_number":"HL-001","name":"Шлем M"}'
```

Отчёты:

```bash
curl http://127.0.0.1:8000/api/v1/reports/summary
curl http://127.0.0.1:8000/api/v1/vehicles/beginner
curl http://127.0.0.1:8000/api/v1/inventory
```

Поддержанные типы транспорта: `scooter`, `bicycle`, `electric_bicycle`. Вещи: `helmet`, `docking_station`, `charging_cabinet`.

## Структура и логика решения

```text
app/
├── api/                 # HTTP-схемы, маршруты, преобразование DTO ↔ домен
├── application/         # сценарии FleetService и отчёт FleetSummary
├── core/                # Settings на pydantic-settings
├── domain/              # сущности, интерфейсы (Protocol), ошибки
├── infrastructure/      # in-memory репозиторий и реальный техосмотр
├── cli.py               # консольная демонстрация
├── container.py         # composition root, dependency-injector
└── main.py              # фабрика FastAPI
tests/                   # unit- и API-тесты, fake техосмотра
```

`InventoryObject` задаёт обязательные имя и инвентарный номер. `Vehicle` добавляет показатель простоты 1–10. Протоколы `Inventoriable` и `EnergyConsumer` в `app/domain/interfaces.py` описывают требуемые абстракции; классы удовлетворяют им структурно, без искусственной глубокой иерархии. Энергия представлена `Decimal`, чтобы отчёты не накапливали ошибки `float`.

`FleetService` зависит только от портов `FleetRepository` и `ServiceCenter`. `Container` из `dependency-injector` создаёт singleton-репозиторий, техосмотр и сервис. HTTP и CLI используют один и тот же прикладной сервис. Транспорт сначала проверяется `ServiceCenter`, и лишь затем попадает в репозиторий. Вещи ставятся на баланс без техосмотра. Уникальность инвентарного номера проверяется для всех объектов в одном месте.

Базовый техосмотр отклоняет энергопотребляющее транспортное средство, если его расход превышает `VYSHKAT_MAX_DEVICE_DAILY_ENERGY_KWH`. Механический велосипед проходит энергетическую часть проверки. Правило для новичков задаётся `VYSHKAT_BEGINNER_THRESHOLD` (по умолчанию 6).

Хранилище намеренно находится в памяти: это соответствует учебной задаче без требования постоянного хранения. После перезапуска процесса данные очищаются.

## SOLID без декоративной архитектуры

- **S — Single Responsibility.** Доменные классы хранят инварианты (`app/domain/models.py`), `BasicServiceCenter` принимает решение техосмотра, `InMemoryFleetRepository` хранит объекты, API отвечает только за HTTP.
- **O — Open/Closed.** Новый транспорт реализуется новым подклассом `Vehicle`; расчёт энергии использует протокол `EnergyConsumer`, а правило новичка работает через базовый `Vehicle`. Прикладной сервис и отчёты менять не нужно.
- **L — Liskov Substitution.** `Scooter`, `Bicycle` и `ElectricBicycle` взаимозаменяемы в операциях с `Vehicle`: каждый имеет корректные инвентарные данные и показатель простоты.
- **I — Interface Segregation.** `Inventoriable`, `EnergyConsumer`, `ServiceCenter` и `FleetRepository` — отдельные небольшие контракты. Шлем не обязан притворяться потребителем энергии.
- **D — Dependency Inversion.** Наиболее явно применён в `app/application/services.py::FleetService`: он принимает `ServiceCenter` и `FleetRepository`, а реализации выбираются только в `app/container.py::Container`. Unit-тест подменяет provider техосмотра через DI-контейнер.

### Сознательное ограничение принципа

SRP применён прагматично: `FleetService` объединяет команды приёмки и простые запросы отчётов. Их разделение на отдельный handler для каждого use case дало бы много файлов без новой бизнес-ценности при текущем размере проекта. Когда появятся БД, транзакции, права доступа или независимое масштабирование чтения и записи, сервис разумно разделить.

## Ответы на обязательные вопросы

### Какой принцип виден наиболее явно?

DIP: `FleetService` не создаёт репозиторий и `ServiceCenter`, а получает абстракции в конструкторе. Конкретные реализации связываются в `app/container.py`. Это позволяет заменить инфраструктуру без изменения бизнес-правил.

### Какой принцип «почти нарушен»?

SRP ограничен агрегирующим `FleetService`, как описано выше. Для небольшого учебного приложения это уменьшает случайную сложность и не смешивает доменную логику с HTTP или хранением.

### Что произойдёт при расширении?

- Новый вид транспорта: добавить подкласс `Vehicle`, а для API — входную Pydantic-схему и одну ветку mapper. `FleetService`, репозиторий, отчёты и CLI-правила не меняются. Если транспорт потребляет энергию, он структурно реализует `EnergyConsumer` полем `daily_energy_kwh`.
- Сотрудник: не наследуется от `InventoryObject`, поэтому случайно не попадёт на баланс. Понадобятся отдельная модель, репозиторий, сервис и API-маршрут; текущая модель парка не сломается.
- Склад запчастей: простые инвентарные запчасти могут наследовать `InventoryObject`. Для количества однотипных позиций и движений склада потребуется отдельный складской агрегат, но отчёт парка продолжит работать.

### Какой тест фиксирует техосмотр и правило новичков?

`tests/test_fleet_service.py::test_rejects_vehicle_when_fake_inspection_refuses` создаёт `FakeServiceCenter(False)` и через `container.service_center.override(providers.Object(fake))` подменяет provider DI-контейнера. Тест проверяет и вызов fake, и отсутствие отклонённого транспорта в парке. `test_reports_inventory_energy_and_beginner_rule` фиксирует граничное значение: простота 6 включается, 5 — нет.

### Что сделал ИИ, а что сделал автор?

ИИ использовался как инструмент: помог разобрать ТЗ, предложил первый вариант структуры, реализацию, тесты и текст README. Автор самостоятельно задал ключевые ограничения (FastAPI, `pydantic-settings`, обязательное разбиение на папки), выбрал итоговый стек и несёт ответственность за проверку, понимание и защиту решения. Перед сдачей автор должен лично запустить тесты, прочитать каждый модуль и уметь изменить правило техосмотра или добавить новый тип транспорта без подсказки.

## Соответствие функциональным требованиям

| Требование | Реализация |
|---|---|
| Добавление транспорта | `POST /api/v1/vehicles`, `FleetService.add_vehicle` |

| Устройства для новичков | `GET /api/v1/vehicles/beginner`, порог из Settings |

| DI и подмена техосмотра | `Container`, `tests/fakes.py` |
| Поведенческие unit-тесты ≥ 60% | `pytest` + `pytest-cov`, усиленный fail-under 80 |
